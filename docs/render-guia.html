Esse é o caminho de toda informação da loja. O navegador nunca fala direto com o Render: ele pede tudo para o próprio endereço da loja, e o Vercel encaminha. É isso que mantém o login seguro e a API protegida.

Quando isso acontece, a loja mostra "Carregando catálogo… o servidor pode levar alguns instantes", em vez de parecer vazia. É comportamento esperado do plano, não defeito.

2. A viagem de um clique

Quando alguém abre a loja, o navegador não pede os produtos "ao Render": pede para o próprio endereço da loja. O caminho real de cada chamada é este:

  1. O navegador chama ferchumodas.shop/api/v1/products.
  2. O Vercel reconhece o trecho /api, carimba a chamada com o crachá secreto e o IP real do visitante, e encaminha para o Render.
  3. O Render confere o crachá. Se estiver certo, atende; se não, responde 403 (veremos adiante o que isso significa).
  4. A API busca os dados no Supabase e devolve um JSON ("resposta organizada em texto") — a lista de produtos com preço, cores, tamanhos e fotos.
  5. A loja monta a tela com esse JSON. Pronto: é o que aparece na vitrine.
Exemplo real, medido em 16/10/2026:

GET https://ferchumodas.shop/api/v1/products
→ 200 · 8 produtos devolvidos
→ o próprio painel de Logs registrou: "GET /api/v1/products 200 · 1826ms"

Login, pedidos e uploads fazem a mesma viagem. A única diferença é que, para comprar ou entrar, o servidor também entrega ao navegador um "crachá de visitante" — o cookie de sessão — para reconhecer a pessoa nas próximas chamadas.

3. Quem é quem (e por que existe cada peça)

A vitrine — Vercel

É a porta da frente: entrega as páginas do site rápido, do servidor mais próximo de quem visita. Ela também é recepção: todo pedido para /api passa por ela antes de chegar ao Render.

Se uma configuração obrigatória faltar, a publicação é cancelada de propósito — melhor não publicar do que publicar uma loja quebrada.

O porteiro — o encaminhamento com crachá

São dois arquivos da loja (vercel.mjs e middleware.js) que colocam na chamada um segredo compartilhado (x-ferchu-proxy-secret) e o IP verificado do visitante (x-ferchu-client-ip). Só o Vercel sabe esse segredo; ele nunca vai para o navegador de quem visita.

Por isso a API responde 403 para qualquer acesso direto que não venha da recepção.

Os fundos — a API no Render

É um programa (Node/Express) que roda em um servidor no Render, na Virgínia (EUA). Ele recebe pedidos de dados, conversa com o banco e responde em JSON. Também cuida de: sessões de login, senhas (com hash), reserva de estoque dos pedidos, uploads de imagem e um diário de bordo (logs).

Uma rota pública de propósito: /health — uma placa de "estou funcionando" que qualquer um pode consultar.

O estoque — Supabase

É onde tudo mora de verdade: catálogo, clientes, pedidos, sessões e as imagens da loja. A API conversa com ele usando um login restrito do próprio back-end — nunca o administrador geral — com permissão apenas para o necessário.

Os pedidos guardam "fotos" dos dados do momento (nome, cor, tamanho, preço, link da imagem), então mudar um produto depois não reescreve pedidos antigos.

Pequeno glossário

API: um "atendente" que recebe pedidos de dados e responde em texto organizado em vez de páginas bonitas. JSON: esse texto organizado. Deploy: publicar uma nova versão no ar. Cookie de sessão: o crachá que o navegador guarda depois do login. Proxy/encaminhamento: repassar uma chamada de um lugar para outro, com regras.

5. Diário das falhas reais (e o que cada erro queria dizer)

Nada disso é "erro escondido": são episódios reais desta publicação, com o significado de cada um em linguagem simples.

O que apareceuO que eraComo terminou
Vercel recusou publicar pedindo RENDER_BACKEND_URL e ORIGIN_PROXY_SECRETA proteção "fail-closed": sem saber o endereço real do Render e o crachá, a publicação para em vez de colocar no ar uma loja apontando para o lugar erradoAs duas configurações foram preenchidas no painel do Vercel (com o mesmo crachá do Render) e a publicação passou
Site respondia 403 "Acesse os dados pelo endereço da loja"O crachá do Vercel e o do Render estavam diferentes (aconteceu na troca da chave) — o porteiro recusava a própria recepçãoMesmo valor salvo nos dois painéis + nova publicação dos dois lados: voltou a funcionar
Erro 400 INVALID_PROXY_IPO Render reescreve cabeçalhos padrão de servidor (como x-real-ip) ao receber a chamada; o IP do visitante chegava "apagado" e a API recusava com razãoCriado um cabeçalho próprio (x-ferchu-client-ip) preenchido pelo Vercel com o IP verificado — e só depois do crachá. Nunca confiar em cabeçalho padrão reescrito pelo caminho
Erro 403 FORBIDDEN ao chamar a API diretoÉ o porteiro funcionando: chamada sem cracháNão é para "consertar" — é a proteção. Só se acessa pelos endereços da loja
Por que não "afrouxar" a proteção para sumir com os 403: sem o crachá, qualquer pessoa na internet poderia ler pedidos e clientes direto da API. O caminho certo é sempre pela loja.

6. O que ainda não foi testado — e por quê

AssuntoSituação honesta
Upload de imagemAdiado de propósito. O sistema não tem exclusão de mídia: uma imagem de teste ficaria para sempre no acervo. O teste fica para a primeira imagem real que você for cadastrar — aí o upload é útil de verdade, e eu acompanho.
Dormência do Render (cold start)O mecanismo é conhecido (aviso na tela, primeiro acesso lento depois de ~15 min parado). Medir o tempo exato exige deixar o serviço dormir de verdade; quando acontecer naturalmente, vale anotar o tempo aqui.
Limite de acessos por visitante (rate limit)Foi testado que IPs forjados são recusados. Provar "dois visitantes diferentes têm limites separados" exigiria duas conexões de internet distintas — teste manual para uma próxima oportunidade (ex.: celular no 4G + computador).

7. Coisas que qualquer pessoa pode conferir sozinha

Na loja

  • Abrir ferchumodas.shop e ver os produtos com foto e preço
  • Entrar com sua conta e ver o painel de gestão

Na proteção

  • Abrir o endereço direto da API e ver o 403 — é a proteção funcionando, não um defeito
  • Abrir /health e ver a placa "estou funcionando" ({"status":"ok"})

8. Referência técnica (só para quem for mexer)

OndeO que fica lá

Variáveis: conexão restrita do banco, FRONTEND_ORIGIN, ORIGIN_PROXY_SECRET (mesmo valor do Vercel), chaves do Supabase Storage, sessão e limites de log/upload.
