1. Estado da publicação

Preparação concluída; publicação em andamento. Origem confirmada: https://ferchumodas.shop. O endereço do Render só será considerado real após a criação e consulta da hospedagem.

Já foram preparados: Node fixado, health check, proxy autenticado, respostas sem cache, proteção de IP/rate limit, fila de logs limitada, desligamento com prazo e recuperação do frontend.

Free é para configurar e validar. Ele dorme após 15 minutos sem tráfego e pode demorar cerca de um minuto para iniciar. Há cotas de horas, banda e builds. Não usar pings para mantê-lo artificialmente acordado. Para uma loja que depende de vendas, avaliar compute pago antes de produção real — nenhum upgrade está autorizado automaticamente.

Para gerar o segredo do proxy no seu próprio terminal, sem compartilhá-lo no chat:

Cole esse valor somente em ORIGIN_PROXY_SECRET nos dois painéis. Ele não é a chave de API do Render. Não preencher ADMIN_EMAIL/ADMIN_PASSWORD nem RENDER_API_KEY na loja.

4. Conectar o Vercel ao Render

Este projeto usa vercel.mjs, não um hostname fixo ou placeholder dentro de vercel.json. A configuração lê o endereço real informado no painel e injeta o segredo no encaminhamento HTTP sem enviá-lo ao navegador.

Vercel → Environment Variables → ProductionValor
RENDER_BACKEND_URLOrigem HTTPS real do Render, sem /api, sem caminho e sem credenciais
ORIGIN_PROXY_SECRETMesmo segredo configurado no Render
VITE_API_URL/api/v1 (também é o padrão do frontend em produção)
Nenhum segredo começa com VITE_. Não criar VITE_ORIGIN_PROXY_SECRET, VITE_DATABASE_URL ou VITE_SUPABASE_SECRET_KEY. Tudo com VITE_ pode ir para o JavaScript público.

Depois de salvar, fazer novo deploy do frontend. A configuração ausente faz o build falhar antes de substituir o site atual: é uma proteção, não motivo para remover a validação. Não adicionar outro vercel.json junto de vercel.mjs.

A mesma origem preserva o cookie HttpOnly; Secure; SameSite=Lax. Não é necessário relaxar para SameSite=None ou liberar qualquer domínio *.vercel.app.

5. Verificar de ponta a ponta

A história completa é: navegador → ferchumodas.shop/api → proxy Vercel → Express no Render → Supabase → JSON → tela. Build aprovado sozinho não prova esse fluxo.

6. MCP do Render no OpenCode

É o controle de gerenciamento, não parte da loja. O MCP já foi consultado nesta sessão. Endpoint oficial: https://mcp.render.com/mcp.

opencode mcp add render --global --url https://mcp.render.com/mcp
opencode mcp list

Para OAuth, abrir /mcps, escolher render e autorizar no navegador. Se este cliente não conseguir registrar a autorização, usar API key por variável de ambiente, não uma chave literal no arquivo:

{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "render": {
        "type": "remote",
        "url": "https://mcp.render.com/mcp",
        "oauth": false,
        "headers": { "Authorization": "Bearer {env:RENDER_API_KEY}" }
      }
    }
  }
}

Mesclar com a configuração global existente, sem apagar outros MCPs. A chave de gerenciamento não vai para o repositório nem para as variáveis do backend.

Por que aparecia connected, mas respondia unauthorized?

A variável estava salva no Windows, mas o processo do OpenCode tinha sido iniciado sem ela. Um terminal antigo pode herdar o ambiente antigo. A correção usada foi carregar explicitamente a variável do usuário antes do reinício:

$env:RENDER_API_KEY = [Environment]::GetEnvironmentVariable("RENDER_API_KEY", "User")
opencode service restart

Só usar se a chave já estiver salva nesse escopo. Não imprimir, colar no chat ou trocar a chave sem necessidade. Connected prova o transporte; listar workspaces prova a autorização.

Pedidos seguros ao agente

  • “Liste workspaces e use somente o que eu confirmar.”
  • “Leia o último deploy e os logs desta hospedagem, sem mostrar segredos.”
  • “Explique a falha antes de alterar configurações.”
Exigir aprovação para deploys, criação de recursos e alterações de plano. O comando MCP de atualizar envs substitui a lista completa: não enviar apenas uma variável como se fosse patch.

7. Problemas comuns e rollback

SintomaVerificar
API Render responde 403Sem proxy, é esperado. Pelo site, conferir segredo igual nos dois painéis e novo deploy.
Vercel falha por RENDER_BACKEND_URLFalta a origem real do Render. Não inserir URL inventada ou localhost.
Login não persisteVITE_API_URL=/api/v1; origem exata https://ferchumodas.shop; verificar Set-Cookie pelo site, não entre domínios diferentes.
Backend não iniciaNode/Root Directory, DATABASE_URL restrita, FRONTEND_ORIGIN HTTPS, segredo com 32–256 caracteres e build Prisma.
Vercel MCP retorna 403/404Reautorizar a integração na conta/time corretos. O acesso ao Render não concede acesso ao Vercel. Usar o dashboard para configurações pendentes, sem compartilhar tokens.
Upload retorna 503Outro upload está em processamento; aguardar e repetir manualmente. Não desativar limite de memória.
Logs não persistemConexão/grants e status de migrações. Não rodar seed. A fila é limitada; stdout contém registros redigidos e contadores de perda.

Rollback: manter SHA e configuração testados. Restaurar versões de frontend/backend compatíveis com o mesmo banco; não resetar PostgreSQL nem apagar histórico de migrações. O frontend antigo com produtos embutidos não substitui o fluxo real de pedidos.

Dependências: os avisos crítico/moderado em proxy-addr/qs foram corrigidos no lockfile. Restam três avisos ligados ao Prisma/Config/deepmerge-ts; revisar patch compatível separadamente. Não executar npm audit fix --force, que sugere downgrade incompatível. Não considerar a loja auditada só porque os testes passaram.
