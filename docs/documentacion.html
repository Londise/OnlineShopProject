1. Arquitectura y mapa del proyecto

Navegador: React 19 / Vite 6
  → Vercel: frontend + proxy /api/*
  → Render: Node 22 / Express 5
  → Prisma 6.19.3 → PostgreSQL, schema privado app
  → Supabase Storage: archivos del bucket storefront-images

En producción el navegador solicita datos al mismo dominio de la tienda, por ejemplo /api/v1/products. Vercel autentica el salto hacia Render; Express valida la solicitud, consulta PostgreSQL y devuelve JSON. El navegador sí puede descargar imágenes directamente del bucket público: no consulta directamente las tablas ni debe conocer secretos del servidor.

Supabase aloja PostgreSQL y Storage; no se usa Supabase Auth ni Edge Functions. El SDK de Storage se utiliza exclusivamente en el backend. Localmente se puede usar PostgreSQL propio y llamar a Express en http://localhost:3001.

Organización del estado

El estado y su lógica deben permanecer lo más cerca posible del componente que los necesita. Compartir sesión y carrito mediante contextos tiene sentido porque los consumen varias pantallas; no convertir detalles de un modal o filtro en estado global sin necesidad.

Los handlers son funciones async nativas: Express 5 deriva sus rechazos al middleware central de errores. Se retiró el envoltorio manual redundante; un test HTTP verifica tanto errores inesperados como errores de negocio, JSON y contexto de traza.

Preparar una base local nueva

  1. Instalar ambos paquetes en sus respectivos directorios.
  2. Copiar server/.env.example a server/.env solo si no existe. Conservar las credenciales locales existentes; completar URLs y origen sin compartir valores.
  3. Preparar PostgreSQL y una conexión administrativa; ejecutar validate, generate y deploy desde server/. La cuenta de migración debe poder crear el grupo técnico.
  4. Provisionar mediante herramienta administrativa segura un LOGIN dedicado y conceder GRANT ferchu_backend TO <login_backend>. La migración crea un grupo NOLOGIN sin contraseña, no la cuenta runtime. Usar la URL del LOGIN restringido en DATABASE_URL.
  5. Ejecutar db:check; únicamente si la base es nueva, vacía y de desarrollo, configurar las variables de admin y ejecutar seed.
  6. Configurar el frontend con VITE_API_URL=http://localhost:3001/api/v1. Arrancar backend y frontend en terminales separadas.
Estas instrucciones describen procedimientos, no autorizan ejecutarlos contra producción. Los tests aislados no reemplazan comprobar conectividad, API y concurrencia en un entorno controlado. No ejecutar seed, migrate dev, db push ni migrate reset sobre datos reales.

3. Configuración y conexiones

PostgreSQL: runtime y administración separados

Obtener el host real desde Connect → ORM → Prisma. Para el servidor persistente: conexión directa si la red soporta IPv6; con IPv4, Session pooler en 5432. No usar Transaction pooler (6543) para migraciones. Codificar la contraseña en la URL, usar schema=app y sslmode=require para remoto; validar el certificado según el entorno. Limitar conexiones, por ejemplo connection_limit=5.

# Plantillas, no valores utilizables; no incluirlas en el bundle del frontend.
DATABASE_URL="postgresql://LOGIN_RESTRINGIDO:CLAVE_CODIFICADA@HOST:5432/postgres?schema=app&sslmode=require&connection_limit=5"
DIRECT_URL="postgresql://LOGIN_OWNER:CLAVE_CODIFICADA@HOST:5432/postgres?schema=app&sslmode=require"

DATABASE_URL pertenece al login miembro de ferchu_backend, no a postgres. DIRECT_URL es la conexión owner usada por Prisma Migrate y debe quedar fuera del runtime productivo. Si Prisma generate requiere DIRECT_URL en Render, repetir allí la URL restringida de runtime: no ejecutar migraciones con ella.

El pool limita conexiones abiertas, no cantidad de visitantes. El README anterior citaba 60 conexiones directas y 200 clientes de pooler para Nano/Micro: son cifras históricas orientativas, no límites garantizados del proyecto actual. Consultar Compute and Disk y Observability → Database del proveedor antes de dimensionar. Auth, Storage y PostgREST también pueden consumir conexiones directas. Si el pooler se agota puede rechazar nuevas conexiones hasta que se liberen; aumentar compute cambia límites, pero no reemplaza controlar el pool.

4. Recorrido de una petición y sesión

app.use() registra middlewares en orden. Cada uno puede enriquecer req, responder o llamar next() para continuar. No todos los requests recorren todo el pipeline: una protección puede terminarlos antes.

  1. Trace y request logger crean el contexto; Helmet aplica cabeceras y /api recibe políticas no-store.
  2. /health consulta SELECT 1 y responde {"status":"ok"} si la base responde; está antes de la protección del proxy y de la sesión.
  3. En /api, requireProxyOrigin valida secreto e IP cuando se configura el proxy. Luego CORS admite el origen configurado y credenciales.
  4. express.json() limita JSON a 100 KB; cookieParser() interpreta el header Cookie y completa req.cookies.
  5. verifySameOrigin() omite GET/HEAD/OPTIONS y rechaza un Origin presente que no coincida con FRONTEND_ORIGIN. Actualmente no rechaza por sí solo una mutación sin Origin: no presentarlo como una verificación universal de CSRF.
  6. attachUser() toma el token del cookie, calcula su hash y busca sesión no revocada y no vencida con usuario activo. Solo entonces asigna el usuario de la base a req.user y actorId al contexto de traza.
  7. Se aplican limitadores, router, validadores, autorización y controller; al final, manejadores de 404/errores.

Ejemplo: GET /api/v1/auth/me

Cookie con token opaco → hash → auth_sessions + users
  → req.user (si la sesión sigue siendo válida)
  → authRouter.get('/me', me)
  → publicUser(req.user) o null
  → JSON { user: ... }
  → api.auth.me() → AuthContext → React actualiza la interfaz

Corrección de las notas originales: el cookie no contiene el objeto del usuario ni su rol. El servidor recupera esos datos desde la base. PublicUser devuelve solo id, name, email y role, nunca passwordHash ni tokenHash. Una visita a /me sin sesión válida devuelve {"user":null}, no equivale necesariamente a un error de conexión.

El registro crea cuentas CUSTOMER; las contraseñas se almacenan con Argon2id. Login valida usuario activo y hash, sin diferenciar públicamente entre cuenta inexistente y contraseña incorrecta. Las sesiones guardan solo el hash del token. El cookie es HttpOnly, SameSite=Lax, path=/ y Secure en producción, con plazo configurado (14 días por defecto). Logout revoca la sesión en la base y borra el cookie; responde 204.

Permisos reales

  • Públicos: catálogo, banners y site-media; POST /orders admite pedido invitado. El proxy no vuelve privado el catálogo para usuarios de la tienda.
  • Autenticado: GET /orders/me devuelve pedidos asociados a la cuenta. Un pedido invitado no se vincula automáticamente por compartir email.
  • STAFF o ADMIN: API administrativa de pedidos e inventario.
  • Solo ADMIN: gestión de catálogo, categorías, opciones, staff, imágenes, banners y logs.
  • El frontend /management exige ADMIN. Que la API permita ciertas operaciones a STAFF no significa que esa página les dé acceso.

Transporte y reintentos

El cliente HTTP usa credentials:'include', genera x-trace-id y conserva el trace de la respuesta. Timeout por intento: 95 segundos; GET/HEAD pueden reintentarse una vez, con espera de 1 segundo, ante fallas reintentables (red, timeout, 502/503/504 o determinadas respuestas inválidas). POST/PATCH/DELETE no se repiten automáticamente. Un HTML de arranque del hosting no se convierte en catálogo vacío ni en cierre de sesión exitoso.

5. Dominio: catálogo, carrito, pedidos y stock

Catálogo y medios

Una categoría agrupa productos; un producto tiene opciones de color o estampa (COLOR/PRINT); cada combinación de opción y talle crea una variante con SKU y stock propio. El precio de variante puede sobrescribir el del producto. Las cantidades monetarias usan centavos enteros y los pesos, gramos. El catálogo, sus galerías y categorías vienen de la base; Home carga banners y favicon desde la API. Si falla la carga se muestra error/placeholder, no productos ficticios locales.

Tablas modeladas: users, auth_sessions, media_assets, categories, products, variant_options, product_options, sizes, product_variants, inventory_levels, orders, order_items, inventory_movements, product_images, site_banners y audit_logs. Los logs operativos se agregan por SQL y no forman parte del schema Prisma.

Listado y detalle públicos filtran categorías, productos, opciones globales, opciones de producto, variantes y talles activos. La administración puede consultar registros inactivos para gestionarlos; no confundir ocultar de la tienda con borrar historial.

Stock y carrito no son lo mismo

disponible = onHand − reserved. El carrito del navegador no reserva stock en la base. Para el modal, además se descuentan las unidades de esa variante que ya están en el carrito: si el disponible publicado es 10 y el carrito contiene 2, puede agregar otras 8. Si el 10 fuese stock físico con reservas pendientes, primero habría que descontar esas reservas. El dato de pantalla es orientativo y puede quedar desactualizado; el backend siempre vuelve a validar al crear el pedido. Los carritos persistidos reconcilian imágenes, sin inventar productos de respaldo.

Creación de pedidos

El carrito persistido valida cada línea y rechaza cantidades no enteras seguras o datos corruptos. La selección usa talles del catálogo y el precio de cada variante. Una entrada vacía de inventario no significa cero: se rechaza también al pulsar Enter. Las respuestas de una pestaña administrativa abandonada no pueden sobrescribir la pestaña actual.

Después de recibir la confirmación de creación, Checkout muestra el número del pedido, retira del carrito las cantidades enviadas y ofrece un enlace normal para abrir WhatsApp; abrirlo no crea otro pedido ni depende de un popup tras una espera. Si se agregaron otras piezas durante la espera, no se borra todo el carrito. La protección contra doble envío vale durante ese montaje, no es idempotencia durable: una respuesta perdida sigue requiriendo conciliación antes de repetir la compra. Cambiar CEP o peso invalida la estimación anterior.

  1. Validar entrada y agrupar líneas repetidas de una misma variante.
  2. Exigir mínimo total de 15 piezas, único mínimo de negocio, también al editar ítems.
  3. Cargar variantes activas, opciones/productos/talles activos y bloquear inventarios en orden determinístico.
  4. Calcular precios, peso y envío en servidor, no aceptar los totales del carrito como autoridad.
  5. Crear pedido NOVO con snapshots de nombre, opción, talle, URL de imagen, precio y peso; registrar reserva y auditoría dentro de la misma transacción.

Se asocia userId si quien compra es CUSTOMER; para invitado o personal no se crea esa asociación de cliente. Las transacciones Serializable tienen como máximo tres intentos ante conflictos reintentables; no introducir llamadas externas ni efectos irreversibles dentro de su función. Los constraints impiden onHand/reserved negativos y reserved mayor que onHand.

Crear y editar pedidos validan también la aritmética agregada: cantidades repetidas, importes de línea, subtotal, peso, envío, total y pagos deben ser enteros seguros dentro de 0…2147483647. Un desborde responde 422 ORDER_AMOUNT_OVERFLOW antes de las escrituras; no se amplían columnas ni se reescriben migraciones para aceptar importes inválidos.

Decisiones comerciales que requieren confirmación

  • Al editar artículos, el subtotal se recalcula pero la cotización de envío existente se conserva. Si cambia el peso, puede dejar de coincidir con la estimación actual: decidir si se debe recotizar o tratarla como precio acordado antes de cambiar esta regla.
  • Los pedidos invitados reservan stock sin caducidad automática. Definir vencimiento, conciliación y comunicación al cliente antes de añadir cancelaciones automáticas; por ahora liberar mediante el flujo administrativo de cancelación.
  • Un timeout de creación puede ocultar un pedido ya guardado. La prevención de doble clic no reemplaza una futura política de idempotencia y recuperación.
Transiciones y movimientos por cada cantidad q
CambioEfecto
Crear NOVOreserved += q (ORDER_RESERVE).
NOVO → CONFIRMADOonHand -= q y reserved -= q (ORDER_CONSUME).
NOVO → CANCELADOreserved -= q (ORDER_RELEASE).
CONFIRMADO → CANCELADOonHand += q (ORDER_RESTORE).
CANCELADO → NOVOVuelve a reservar q si hay disponibilidad suficiente.
CONFIRMADO → CONCLUIDONo mueve nuevamente stock. CONCLUIDO no tiene transición de salida.

Repetir el mismo estado no duplica el movimiento. Editar ítems ajusta reservas si está NOVO o existencia consumida si está CONFIRMADO; CANCELADO no mueve stock y CONCLUIDO no permite editar ítems. Se conservan los snapshots previos de variantes existentes; nuevas líneas toman datos vigentes. Cambiar el catálogo no reescribe pedidos históricos.

Archivar no borra el pedido: lo marca con archivedAt/archivedById y registra auditoría. Si estaba NOVO o CONFIRMADO se cancela, liberando/restaurando inventario; cancelación, movimientos, auditorías y archivo se confirman en una sola transacción Serializable. Ya no existe un intervalo entre dos confirmaciones donde otro operador pueda reabrirlo y dejar reservas en un pedido archivado. No se documenta como restauración reversible desde el panel: no hay aquí una ruta de desarchivado. Las pruebas nuevas de intercalado y rollback usan un adapter en memoria; no sustituyen una prueba de concurrencia del motor PostgreSQL.

Envíos y pagos: límites de lo implementado

CORREIOS valida CEP de 8 dígitos y calcula un PAC estimado local según primer dígito y peso, redondeado a intervalos de 0,5 kg con mínimo 0,5 kg. No es una cotización de una integración externa con Correios. EXCURSAO deja el importe de envío en null para confirmarlo después; el total suma cero hasta que haya importe aplicable. El peso y monto de envío se fijan al crear; la edición de ítems no recalcula automáticamente ese envío.

paidAmountCents es un importe registrado al administrar el pedido. No demuestra que haya cobro automático ni webhook de proveedor implementado. Los ejemplos anteriores de payment.webhook_failed, reintentos de pago y shipping.quoted eran ilustraciones, no funciones reales de esta tienda; no se usan como evidencia ni como procedimiento operativo.

6. PostgreSQL, migraciones e importación

Todos los modelos y enums declaran explícitamente @@schema("app"). Mantener app privado y fuera de los schemas expuestos por la Data API. No gestionar las mismas tablas con migraciones Prisma y Supabase CLI simultáneamente.

No editar una migración ya aplicada; generar una nueva para cada cambio. Toda tabla nueva necesita grants explícitos restringidos y RLS apropiado: los grants iniciales no cubren mágicamente tablas futuras.

Historia MySQL preservada

server/prisma/history/mysql/ contiene las migraciones originales sin alterar, solo como registro de la estructura de origen. No son migraciones activas, no implican soporte MySQL en el runtime y no se aplican en PostgreSQL. No importar la antigua _prisma_migrations. Esta política también se conserva en AGENTS.md.

Importar datos reales a otro ambiente

Crear estructura no copia clientes, hashes, sesiones ni pedidos. No ejecutar seed sobre datos migrados. No crear otra base ni migrar datos simplemente por mover Express de hosting.
  1. Obtener acceso a origen/destino y backup recuperable. Ensayar sobre destino vacío, fuera del runtime.
  2. Preservar IDs, hashes de contraseña, sesiones, snapshots, vínculos de medios y relaciones. No reemplazar autenticación ni reiniciar contraseñas como parte de una copia.
  3. Revisar zona horaria de origen (destino usa timestamptz), unicidades, cantidades, totales, reservas y cada campo; no ocultar inconsistencias rechazadas por constraints.
  4. Pausar escrituras, copiar versión final, reconciliar y probar login/pedidos/inventario antes de cambiar la conexión publicada.
  5. Conservar origen hasta validar copia y respaldo. No desinstalar servicios que puedan alojar bases de otros proyectos. Las herramientas temporales de transferencia no pertenecen a dependencias del backend.

Volver a la conexión antigua después de nuevas ventas puede perder pedidos: un rollback exige copiar/reconciliar las nuevas escrituras. Las sesiones propias pueden sobrevivir si se preservan registros, token del navegador y las condiciones de cookie, origen y plazo. Ver antecedentes para distinguir la migración documentada anteriormente de una comprobación actual.

7. Imágenes en Supabase Storage

Bucket público storefront-images: lectura pública, escritura exclusivamente a través de Express con sesión ADMIN y controles de origen/proxy. No conceder escritura pública ni modificar objetos mediante SQL en el schema storage. SUPABASE_SECRET_KEY vive solo en secretos del backend.

  • Gestión → Imágenes permite subir para producto, categoría, banner o favicon, y ordenar/elegir portada.
  • JPEG, PNG y WebP no animados; hasta 5 MB y 16 megapíxeles. Se decodifica el contenido, no se confía solo en la extensión/MIME declarado.
  • POST /api/v1/admin/uploads: multipart con file, purpose, targetId cuando corresponda, optionId opcional para producto, primary, sortOrder y altText.
  • GET /api/v1/admin/media-assets lista la biblioteca; PATCH /api/v1/admin/product-images/:id actualiza portada/orden.
  • Rutas de objetos inmutables: cambiar portada no sobrescribe archivos anteriores. No hay eliminación de objetos desde el panel. Una URL vieja puede estar en snapshots de pedidos: no borrarla ni sobrescribirla.
  • MEDIA_UPLOAD_CONCURRENCY=1 limita el trabajo completo para reducir memoria, especialmente en instancias de 512 MB. Exceso devuelve 503; no repetir automáticamente POST.

Manifiesto y transición de medios

server/prisma/data/storage-images.json conserva el mapa público sin claves. El registro anterior describe 27 imágenes originales migradas sin recompresión y verificadas por SHA-256; no equivale a una verificación hecha ahora. npm run media:migrate -- --verify, ejecutado desde server y con autorización para acceder al destino, vuelve a comprobar descargas y registros.

El importador admite --assets-dir=<ruta> y --manifest=<ruta> (rutas relativas al directorio de ejecución o absolutas); conserva los valores predeterminados si se omiten. Comprueba los originales requeridos antes de acceder a Storage. Las pruebas usan directorios temporales, una base descartable y Storage HTTP local: estos argumentos no autorizan usar datos reales. Un conflicto revierte los vínculos y no publica el manifiesto; no promete eliminar objetos nuevos huérfanos.

server/scripts/migrate-images.js necesita los archivos originales para importar; tras retirarlos de los assets locales se utiliza --verify. No borrar objetos existentes si una importación falla. Cloudinary no es dependencia del runtime ni el importador local migra automáticamente una cuenta Cloudinary.

Antes de aplicar storage_media en otro ambiente, inspeccionar media_assets.public_id. Si existen identificadores externos, la migración aborta para evitar pérdida: primero copiar/verificar archivos, conservar IDs y relaciones y actualizar referencias en una transición específica. No quitar el bloqueo ni marcar la migración como aplicada sin hacer esa transición.

8. Seguridad y límites de confianza

Proxy de producción

Vercel middleware.js obtiene el IP verificado por la plataforma y sobrescribe x-ferchu-client-ip junto con x-ferchu-proxy-secret en los headers de la solicitud upstream, no de la respuesta al navegador. Render primero autentica el secreto y luego valida exclusivamente ese IP personalizado. El visitante no puede decidir qué IP debe usar el rate limit enviando una cadena arbitraria.

Express mantiene trust proxy=false. No arreglar INVALID_PROXY_IP confiando en x-forwarded-for, x-real-ip o conteos de saltos: el ingress puede reescribirlos. En local sin secreto se usa el socket; el agrupamiento IPv6 evita tratar direcciones equivalentes como visitantes ilimitados.

El secreto restringe el camino de acceso, pero no reemplaza sesión ni roles. Sin él el catálogo directo en Render también devuelve 403 en producción; eso es intencional. No es correcto afirmar que sin proxy cualquier persona podría leer clientes/pedidos privados: esas rutas siguen requiriendo autorización de aplicación. Nunca debilitarla para ocultar un 403.

Capas de protección

  • CORS permite el origen exacto configurado con credenciales; no equivale a autenticación. La comprobación de Origin tiene el alcance descrito en el pipeline.
  • Cookies HttpOnly/Secure/SameSite, contraseñas Argon2id, sesiones revocables y autorización Express por CUSTOMER/STAFF/ADMIN.
  • Limitadores independientes sobre /api/v1/auth y /api/v1/orders: 20 requests por 15 minutos por clave de cliente en cada montaje, no solo 20 contraseñas erróneas. Son memoria del proceso, no una cuota distribuida persistente.
  • Validación Zod, límites JSON y de medios, SQL parametrizado y transacciones con invariantes de inventario.
  • Cuenta PostgreSQL técnica restringida, schema privado, revocaciones a roles de navegador y RLS como defensa adicional. ferchu_backend no es un usuario CUSTOMER/STAFF/ADMIN: la autorización por persona queda en Express, no en auth.uid().
  • No cachear respuestas /api. No exponer secretos, URLs con contraseña, cookies ni hashes en frontend, documentación, screenshots o logs.

Dependencias

La revisión local del 16/10/2026 ejecutó npm audit en ambos paquetes: cero avisos después de corregir la dependencia transitiva deepmerge-ts. Prisma y su cliente permanecen en 6.19.3; un override acotado a @prisma/config fija deepmerge-ts 8.0.2. El harness nuevo valida/genera el cliente y aplica las migraciones sobre una base descartable; no prueba el algoritmo de merge de una dependencia. Revisar este override cuando Prisma incorpore la corrección. No usar npm audit fix --force ciegamente: puede proponer un downgrade incompatible. Ausencia de avisos, tests y build no sustituyen una auditoría exhaustiva ni certifican seguridad de producción.

10. Logs operativos y auditoría

La telemetría describe salud HTTP, errores y eventos; la auditoría en audit.service.js/app.audit_logs registra actor, entidad y acción, con datos anteriores/posteriores cuando el comando los aporta. No todas las modificaciones guardan una copia completa del antes/después. Son sistemas distintos: no reemplazar auditoría transaccional por un log asíncrono.

Las escrituras de categorías, opciones globales, productos, opciones/variantes/imágenes de producto y creación de STAFF se confirman junto con su auditoría en una única transacción. Una falla al registrar auditoría aborta también ese cambio; no se responde con error después de haberlo confirmado fuera de la transacción. La suite de integración nueva verifica persistencia y rollback con PostgreSQL real; los dobles históricos se retiran a medida que se verifica su sustitución.

Usar Gestión → Logs (ADMIN)

  1. Seleccionar nivel y servicio; se aplican al cambiar. La lista muestra primero los registros más nuevos.
  2. Escribir una búsqueda de evento/mensaje (ejemplo: order.created) y pulsar Filtrar o Enter. No busca dentro de todo el JSON ni es un campo de traceId.
  3. Ao vivo actualiza cada 3 segundos por polling, no por streaming. No garantiza mostrar todos los eventos entre consultas ni anuncia todos los fallos del polling.
  4. Abrir una fila para ver traceId, requestId, actorId, route, status, durationMs, data y stack.
  5. Ver trace completo aplica filtro traceId a la lista; el chip permite quitarlo. La UI conserva orden descendente; no cambia a cronológico ascendente. La ruta específica /trace/:id sí responde ascendente.
  6. Carregar mais usa cursor para avanzar hacia registros más antiguos. El panel pide 60 por página; no es una exportación ilimitada.

El selector ofrece api/storefront/worker como valores; su existencia no prueba que haya workers o emisión de telemetría frontend implementados. El valor habitual del logger es api. Obtener x-trace-id y x-request-id desde Network en el navegador para soporte, sin copiar cookies ni Authorization. Consultar un trace pegado mediante el parámetro traceId de la API, o desde una fila del panel, no mediante búsqueda textual q.

Flujo, límites y garantías reales

server/src/lib/logger.js recibe log(level,event,message,ctx) y helpers logInfo/logWarn/logError, etc. AsyncLocalStorage hereda traza, request y actor desde el contexto; los servicios no necesitan propagar IDs manualmente. Un trace es correlación, no una prueba de identidad ni de que se haya instrumentado cada paso.

Antes de encolar, el logger oculta claves sensibles (password/pass, token, secret, authorization, cookie, senha, API key) y patrones de email, CPF, tarjeta, credenciales en URL, Bearer y ciertos tokens. Limita profundidad, arrays, strings y tamaño de data. No es una garantía de detectar toda PII: no enviar secretos ni datos personales innecesarios y no incluirlos en nombres de eventos.

Los eventos filtrados se reflejan como JSON redactado en stdout fuera de test. La cola en memoria se escribe por lotes con SQL parametrizado en app.log_entry. Si falla intenta app.log_dead; si el mismo banco no está disponible, también puede fallar ese segundo intento: se descarta el lote y se emite logger.persistence_failed. Al saturarse la cola descarta nuevas entradas y emite logger.queue_full con contador. No es una cola durable ni promete entrega exactamente una vez.

Recetas de diagnóstico

  • “Falló mi pedido”: pedir hora y trace; revisar también warn/4xx y red, no solo error. Un request bloqueado antes de Express no aparecerá en sus logs. Correlacionar con pedido real antes de reenviar POST para evitar duplicados.
  • “¿Intentan entrar?”: buscar auth.login_failed y patrones por tiempo/ruta. Muchas fallas no prueban por sí solas un ataque; un mismo trace tampoco equivale a un mismo visitante. Revisar rate limiting e IPs autenticados sin recolectar PII innecesaria.
  • “La tienda va lenta”: http.request, route y durationMs permiten localizar operaciones lentas, no identificar por sí solos la causa (base, red, arranque o CPU).
  • “¿Quién cambió el estado?”: order.status_changed aporta actorId y data.from/to; consultar audit_logs para los datos adicionales capturados por ese comando, sin asumir snapshots completos para cualquier entidad.

Emitir eventos al desarrollar

import { logInfo } from '../lib/logger.js';

// Patrón ilustrativo, no agregar un segundo evento donde ya se emite.
logInfo('order.created', 'Pedido creado', {
  data: { orderId: order.id, totalCents: order.totalCents },

Usar dominio.verbo en minúsculas, mensaje corto y detalles en data; centavos en totalCents y milisegundos en durationMs. Para errores pasar stack cuando corresponda sin secretos. Evitar INFO en loops calientes, no llamar al logger desde su propio flush/dead-letter, y no sustituirlo por console.log para telemetría de aplicación. El stdout interno del logger se usa deliberadamente para diagnosticar su propia falla.

Particiones, retención y dead-letter

La migración log_system crea app.log_entry por RANGE mensual y una partición DEFAULT, más mes anterior, actual y siguiente al aplicar. app.log_dead conserva lotes fallidos. No están en schema.prisma porque Prisma no modela el particionado; no borrarlas por esa diferencia.

app.log_entry_maintenance() crea los próximos dos meses y elimina particiones mensuales según un corte de 90 días calculado desde el inicio del mes. La retención es aproximada, por particiones, no un borrado exacto de cada fila a los 90 días. DEFAULT nunca se elimina y log_dead no tiene limpieza automática en esa función. Si DEFAULT contiene filas de un rango futuro, la creación de su partición puede requerir revisión administrativa y reubicación controlada; no asumir que siempre se mantendrá sola.

Se intenta instalar pg_cron y programar semanalmente el trabajo log-entry-maintenance (domingo 03:17 según horario del scheduler). Falta de extensión/permisos produce avisos y puede dejarlo sin agenda. Comprobar que el trabajo existe y termina correctamente; sin agenda, un administrador debe ejecutar periódicamente la función. Es SECURITY DEFINER, con search_path fijado y EXECUTE revocado a PUBLIC; no convertirla en un endpoint público ni conceder privilegios owner al runtime para operarla.

-- Operación de mantenimiento con permisos administrativos; MODIFICA datos/particiones.
-- No ejecutada para redactar esta documentación.
SELECT app.log_entry_maintenance();
-- Consultas de diagnóstico de SOLO LECTURA, con acceso autorizado.
SELECT ts, event, message, route, duration_ms
FROM app.log_entry
WHERE level >= 50 AND ts > now() - interval '24 hours'
ORDER BY ts DESC LIMIT 100;

SELECT route, count(*) AS requests,
       percentile_cont(0.95) WITHIN GROUP (ORDER BY duration_ms) AS p95_ms
FROM app.log_entry
WHERE event = 'http.request' AND ts > now() - interval '1 day'
GROUP BY route ORDER BY p95_ms DESC;

SELECT failed_at, fail_reason, jsonb_array_length(payload) AS entradas
FROM app.log_dead ORDER BY failed_at DESC LIMIT 20;

Un crecimiento de log_dead requiere revisar permisos, base y particiones. Tras resolver la causa, cualquier reinserción de payload es una operación administrativa revisada: no hay replay automático ni garantía de ausencia de duplicados. Conservar evidencia y aplicar una política explícita de retención de dead-letter/stdout según necesidades de privacidad y soporte.
