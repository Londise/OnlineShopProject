01 O painel de logs

Entre em Gestão (menu admin) e clique na aba Logs. Tudo que a API registra aparece aqui, do mais novo para o mais antigo.

gestão → logs
14:32:07ERRORapipayment.webhook_failed · Webhook falhou após 5 tentativas · pedido #A1042
14:32:05WARNapipayment.webhook_retry · Webhook de pagamento falhou · retry 4/5
14:31:58INFOapiorder.created · Pedido FM-2026-1042 criado
14:31:58INFOapihttp.request · POST /api/v1/orders 201 · 38ms
14:31:41WARNapiauth.login_failed · Tentativa de login falhou

1Filtros (barra superior)

Nível (trace…fatal), serviço (api, storefront, worker) e busca livre que procura no evento e na mensagem — ex.: order.created, webhook, timeout. Clique em Filtrar (ou Enter) para aplicar a busca; os seletores aplicam na hora.

2Botão "Ao vivo"

Liga o live tail: a lista se atualiza sozinha a cada 3 segundos. Ideal para acompanhar um teste em tempo real ("vou criar o pedido agora e ver o que acontece").

3Clicar numa linha

Expande o JSON completo do registro: traceId, requestId, actorId (quem estava logado), rota, status, latência, o contexto (data) e o stack quando é erro.

4"Ver trace completo"

Dentro da linha expandida: filtra a lista para mostrar somente os logs daquela request, em ordem cronológica — do http.request até o erro. É a resposta para "o que exatamente aconteceu nessa operação?". Um chip no topo mostra o trace filtrado; o ✕ limpa.

5"Carregar mais"

Navega para registros mais antigos usando paginação por cursor (sem pular nem repetir linhas, mesmo com logs novos chegando).

Dica: toda resposta da API devolve os headers x-trace-id e x-request-id. Se um cliente reportar erro, o suporte pode pedir o trace (visível na aba Network do navegador) e você cola esse ID na busca do painel.

03 Receitas práticas

🔍 "O cliente disse que o pedido falhou"

  1. Peça o horário aproximado do erro.
  2. No painel, filtre nível error e busque order.
  3. Abra a linha do erro e clique Ver trace completo.
  4. Você verá a sequência inteira: request → validação → banco → erro, com stack.

🛡️ "Estão tentando entrar na minha conta?"

  1. Busque auth.login_failed.
  2. Cada tentativa aparece como warn (o e-mail é redigido por segurança).
  3. Muitas tentativas seguidas no mesmo trace/rota = ataque de força bruta; o rate limit da API já bloqueia após 20 em 15 min.

📈 "A loja está lenta?"

  1. Busque http.request e olhe a coluna de duração (···ms).
  2. Expande uma linha lenta: durationMs alto + rota indicam o gargalo.
  3. Filtre por nível warn/error para ver se há falhas junto.

🧾 "Quem confirmou/cancelou o pedido X?"

  1. Busque order.status_changed.
  2. Expanda a linha: actorId diz quem fez; data.from/to mostra a transição.
  3. Para o antes/depois completo dos campos, isso continua na auditoria (audit_logs), que é separada dos logs.

Consultas rápidas via API (curl)

# erros e fatais de hoje (cookie de sessão ADMIN)
curl --cookie "ferchu_session=SEU_TOKEN" \
  "http://localhost:3001/api/v1/admin/logs?level=error,fatal&limit=50"

# tudo de um trace específico, em ordem
curl --cookie "ferchu_session=SEU_TOKEN" \
  "http://localhost:3001/api/v1/admin/logs/trace/7f3a1c2e-...."

# busca textual + paginação por cursor
curl --cookie "ferchu_session=SEU_TOKEN" \
  "http://localhost:3001/api/v1/admin/logs?q=webhook&cursor=eyJ0...&limit=100"

Consultas diretas no SQL (somente leitura)

-- erros das últimas 24h
SELECT ts, event, message, route, duration_ms
FROM app.log_entry
WHERE level >= 50 AND ts > now() - interval '24 hours'
ORDER BY ts DESC;

-- rotas mais lentas hoje (p95 aproximado)
SELECT route, count(*) AS reqs,
       percentile_cont(0.95) within group (order by duration_ms) AS p95_ms
FROM app.log_entry
WHERE event = 'http.request' AND ts > now() - interval '1 day'
GROUP BY route ORDER BY p95_ms DESC;

04 Emitir logs a partir do código (dev)

Use o logger em server/src/lib/logger.js — nunca console.log para telemetria. Trace, request e usuário logado são herdados automaticamente do contexto da request.

import { logInfo, logWarn, logError } from '../lib/logger.js';

// evento de negócio (INFO)
logInfo('shipping.quoted', 'Frete calculado', {
  data: { method: 'CORREIOS', amountCents: 1420 },
});

// anomalia recuperável (WARN)
logWarn('media.upload_rejected', 'MIME não suportado', {
  data: { mime: file.mimetype, sizeKb: 2400 },
});

// falha (ERROR) — passe o stack
logError('payment.webhook_failed', error.message, {
  stack: error.stack,
  data: { orderId: order.id, attempt: 5 },
});

✅ Boas práticas

  • Evento em dominio.verbo minúsculo: order.created, db.query_timeout.
  • Mensagem curta para humanos; detalhes vão em data (JSON).
  • Centavos em totalCents, milissegundos em durationMs.
  • Em rotas novas, o trace/usuário já chegam de graça — não repasse.

🚫 O que NÃO fazer

  • Não logue senhas/tokens — o logger redige chaves sensíveis, mas evite.
  • Não logue dentro de loops quentes em INFO (use DEBUG: é sampleado).
  • Não chame o logger de dentro dele mesmo (flush/dead-letter usam só console).
  • Não use para auditoria de negócio (quem mudou o quê) — isso é audit.service.js.
Redação automática: e-mail, CPF, cartão e qualquer chave com password|token|secret|authorization|cookie|senha viram [REDACTED] antes de gravar — inclusive dentro de objetos aninhados.

05 Configuração (server/.env)

VariávelPadrãoO que controla
LOG_LEVELinfoNível mínimo gravado (trace…fatal). Em dev, debug ajuda.
LOG_DEBUG_SAMPLE0.1Fração de logs DEBUG gravados (0.1 = 10%). 1 grava todos.
LOG_BUFFER_MAX100Entradas no buffer que disparam flush imediato.
LOG_FLUSH_MS2000Intervalo máximo do buffer antes de gravar em lote.

Em desenvolvimento, cada log também aparece no console da API (uma linha por evento). O flush final acontece no desligamento gracioso (SIGINT/SIGTERM), então Ctrl+C não perde logs.

06 Manutenção e retenção

  • Partições: os logs ficam em app.log_entry, particionada por mês (mais uma partição DEFAULT de segurança). A migração cria o mês anterior, o atual e o seguinte.
  • Criação de partições futuras + limpeza: a função app.log_entry_maintenance() garante os próximos 2 meses e apaga partições com mais de 90 dias (drop instantâneo, sem DELETE em massa). No Supabase ela roda sozinha toda semana via pg_cron (se a extensão existir).
  • Sem pg_cron? rode manualmente de tempos em tempos:
SELECT app.log_entry_maintenance();
  • Dead-letter (app.log_dead): se o banco ficar indisponível no momento do flush, o lote vai para essa tabela com o motivo. Verifique em GET /api/v1/admin/logs/dead ou:
SELECT failed_at, fail_reason, jsonb_array_length(payload) AS entradas
FROM app.log_dead ORDER BY failed_at DESC LIMIT 20;
⚠️ Se a log_dead estiver crescendo, o banco rejeitou gravações de log (queda, permissão ou partição ausente). Resolvido o problema, os lotes podem ser reinseridos manualmente a partir do payload.

07 Problemas comuns

"O painel mostra 403 / não aparece a aba Logs"

A aba e os endpoints exigem sessão ADMIN (STAFF não acessa). Confira se seu usuário é ADMIN e refaça o login.

"Não vejo logs de DEBUG"

Dois motivos possíveis: LOG_LEVEL está acima de debug, ou o sampling (LOG_DEBUG_SAMPLE=0.1) descartou 90% deles de propósito. Em dev, use LOG_LEVEL=debug e LOG_DEBUG_SAMPLE=1.

"Logs somem quando a API reinicia?"

Não: o buffer grava a cada 2s e no desligamento gracioso. Só um crash duro (kill -9, queda de energia) pode perder o buffer dos últimos 2 segundos — trade-off aceito para não bloquear requests.

"E-mail do cliente aparece como [REDACTED]"

É de propósito (LGPD): dados pessoais são redigidos antes de gravar. Para atendimento, cruze o orderId/traceId com o pedido no painel de Gestão.

"Onde ficam os logs de quem alterou o pedido?"

Isso é auditoria de negócio (audit_logs), sistema separado que já existia. Logs operacionais = saúde/erros/telemetria; auditoria = antes/depois por usuário.
