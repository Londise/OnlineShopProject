# Repository notes

- This repo has two independently installed Node packages: the React/Vite storefront at the root and the Express API in `server/`; run commands from the matching directory.
- Frontend commands (root): `npm run dev`, `npm run build`, `npm run preview`; `npm test` runs Node units plus Vitest/Testing Library interactions. `test:unit`, `test:ui`, `test:e2e` and `test:sensitivity` select levels; `npm run test:all` runs frontend, backend, launcher regression, PostgreSQL integration, browser journeys and isolated build sequentially. No lint or typecheck scripts.
- Backend commands (`server/`): `npm run dev` (watch mode) or `npm start`; Prisma tasks are `npm run prisma:generate`, `npm run prisma:migrate -- --name <migration>`, `npm run prisma:deploy`, and `npm run prisma:seed`.
- Backend setup requires PostgreSQL (Supabase or local) and `server/.env`: see `docs/documentacion.html#desarrollo`; application tables live in private schema `app`. Generate Prisma client and apply migrations before starting. Do not seed a database receiving real migrated data. The API defaults to port 3001; frontend API URL is `VITE_API_URL=http://localhost:3001/api/v1`.
- The frontend entrypoint is `src/main.jsx` → `src/App.jsx` → `src/routes/AppRoutes.jsx`; pages live in `src/pages/`, shared state in `src/contexts/`, and API calls in `src/services/api.js`.
- Integration launcher cancellation: use its internal `--startup-timeout-ms=<ms>` (default 110000) and `--timeout-ms=<ms>` (default 600000), or SIGINT/SIGTERM on POSIX; a forked parent can send `{ type: 'cancel' }` over IPC (portable on Windows). It stops owned test workers, then PostgreSQL, before exiting nonzero. Cancellation during startup waits for the current bounded native step. Do not wrap it in a shorter hard-kill timeout: SIGKILL/TerminateProcess cannot run cleanup. `test:harness` checks normal failure, execution timeout and startup cancellation sequentially.
- The API entrypoint is `server/src/server.js`; request routing is under `server/src/routes/`, with handlers in `controllers/` and business logic in `services/`. Prisma schema, migrations, and seed are under `server/prisma/`.
- Preserve Prisma migrations as the database change history; use a new migration for schema changes rather than editing an already-applied migration. `prisma:deploy` applies committed migrations for deployment.
- Original MySQL migrations are historical records in `server/prisma/history/mysql/`, not active migrations. Backend tests: `npm test` in `server/` for units/isolated HTTP-input cases; `npm run test:integration` for Express + Prisma + real PostgreSQL. Its launcher creates a loopback-only cluster with `embedded-postgres`, validates/generates Prisma and deploys committed migrations, then runs as a restricted member of `ferchu_backend`. It ignores configured database URLs and never uses a real bucket. Use Node 22.23.4+ (<23) and a non-root OS user; do not create system users to make tests pass. Install both packages and run `npx playwright install chromium` before E2E. Do not run `test:harness`, integration or E2E simultaneously: all generate the same local Prisma client. Replacement status is recorded in `REGISTRO-REEMPLAZO-TESTS.md`.
- Images live in public Supabase Storage bucket `storefront-images`; privileged Storage keys stay only in backend secrets. Uploads require existing ADMIN sessions. `npm run media:migrate -- --verify` checks the image manifest; never overwrite/delete objects referenced by order snapshots.
- Operational logging: `server/src/lib/logger.js` buffers structured entries and flushes them in batch to `app.log_entry` (monthly partitions + default partition) via raw SQL; `app.log_dead` is the dead-letter for failed flushes. These tables are intentionally NOT in `schema.prisma` (Prisma can't model partitions); they are created by migration `20261013100000_log_system` with RLS + `ferchu_backend` grants. Retention/partition upkeep is `app.log_entry_maintenance()` (pg_cron weekly when available). Query endpoints live under `/api/v1/admin/logs` (ADMIN only); the admin UI is the "Logs" tab in `src/pages/Management.jsx` (`src/components/LogsPanel.jsx`). Tune with `LOG_LEVEL`, `LOG_DEBUG_SAMPLE`, `LOG_BUFFER_MAX`, `LOG_FLUSH_MS`. The per-request `trace-id` flows from `src/services/api.js` → `x-trace-id` header → `server/src/middlewares/trace.js` (AsyncLocalStorage). Business audit stays separate in `server/src/services/audit.service.js`.
- Render deployment: `server/.node-version` pins Node 22.23.4; build from `server/` with `npm ci --include=dev && npm run prisma:generate`, start `npm start`, health `/health`. `server/src/app.js` composes HTTP without listening; `server/src/server.js` owns process lifecycle. Production requires exact HTTPS `FRONTEND_ORIGIN` and `ORIGIN_PROXY_SECRET`. `vercel.mjs` uses server-only `RENDER_BACKEND_URL` and injects that shared secret on `/api/*`; browser uses relative `/api/v1`. Never trust forwarded IP headers without that secret; do not expose it as `VITE_*`. See `docs/documentacion.html#despliegue`. Do not run owner migrations/seed at runtime or create a new database for this hosting move.
- Log queue hard caps: `LOG_QUEUE_MAX_ENTRIES` and `LOG_QUEUE_MAX_BYTES` include in-flight batches; shutdown drains active writes before disconnecting Prisma. Upload concurrency defaults to one (`MEDIA_UPLOAD_CONCURRENCY`). HTTP/read retries never replay mutations such as order creation.
- Vercel `middleware.js` copies the platform-verified IP into `x-ferchu-client-ip` and adds the private proxy secret only to upstream request headers (overwriting visitor input). Render validates only this authenticated custom header, never a standard header chain rewritten by intermediate proxies. Do not bypass `INVALID_PROXY_IP` by trusting arbitrary forwarded headers.
